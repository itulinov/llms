# Этап 05 - сотрудники и учётные записи

## Результат и границы

Административный цикл: создать сотрудника → выдать доступ → изменить данные → заблокировать или уволить → отозвать сессии → восстановить доступ.
Использовать collaborators, accounts, auth_sessions без миграции 005. Оргструктура, назначения должностей, импорт, удаление, создание администраторов и смена ролей через UI вне этапа.

## Сотрудники и API

- Список, поиск по ФИО/коду/email через ILIKE с буквальным экранированием %, _ и обратного слеша; фильтр все/работающие/уволенные.
- limit по умолчанию 25, максимум 100; offset неотрицательный; сортировка fullname,id. items и total в REPEATABLE READ read-only транзакции.
- Поля: code, lastname, firstname, middlename, email, hire_date, dismiss_date, is_dismiss. Фамилия обязательна, необязательные пустые значения null; валидация email и дат. Дата не меняет признак автоматически.
- ФИО вычисляет БД. Должность, подразделение и организация только для чтения из v_collaborators. Остальные поля не изменять.
- GET/POST /api/admin/collaborators; GET/PUT /api/admin/collaborators/{id}; POST .../{id}/account; PUT .../{id}/account/status; POST .../{id}/account/password.
- RequireAuth и RequireRole admin на всех маршрутах; JSON, Origin, 8 KiB. Ошибки 400/401/403/404/409/503.
- PUT передаёт все поля и точный updated_at с микросекундами, без преобразования через JS Date. Конфликт версии под блокировкой даёт 409 без изменений.

## Доступ и конкурентность

- Создавать только employee: логин, пароль, подтверждение; у уволенного неактивная запись. Логин и роль не редактируются.
- Блокировка и новый пароль отзывают все сессии в одной транзакции. Argon2id вне транзакции, пароли и хеши не возвращаются и не логируются.
- Увольнение блокирует запись и отзывает сессии атомарно с кадровой карточкой. Возврат активирует даже вручную заблокированную запись. Сохранение без изменения признака доступ не меняет.
- Предупреждение: «При возвращении сотрудника в штат его доступ к LMS будет автоматически восстановлен».
- Отдельная разблокировка уволенного запрещена. Связанного admin показывать без управления; увольнение последнего активного admin запрещено.
- Единый порядок административных блокировок: advisory lock 2026111301 → collaborators FOR UPDATE → accounts FOR UPDATE. Ключ общий с create-admin. Проверка активных admin после lock.
- Создание сессии: транзакция, accounts FOR UPDATE, повторная проверка активности и проверенного хеша пароля. Уже выполняющиеся запросы не прерываются; после commit блокировки новые проверки отказывают.

## Интерфейсы

- React Admin: список, карточка, создание, доступ; загрузка, пустой список, ошибки, запрет повторной отправки, подтверждение ухода с изменениями.
- Конфликт 409 сохраняет ввод и предлагает загрузить актуальную карточку с подтверждением потери правок.
- Portal остаётся с auth/me: новое ФИО при перепроверке; отозванная сессия ведёт на вход.
- Диагностику разового сбоя и существующий незакоммиченный тест зависшего API не включать.

## Проверки и поставка

- PostgreSQL: поля, ФИО, сохранность дополнительных данных/должностей, поиск, пагинация, конфликты.
- Конкурентность: два редактора (второй 409), два accounts, вход против блокировки/смены пароля, два увольнения admin.
- Проверки прав каждого endpoint, отзыв всех сессий, ручная блокировка → увольнение → восстановление (активен, старые сессии не восстановлены).
- Firefox: формы, поиск, конфликты, предупреждение. Go -race, изолированная PostgreSQL, сборка Admin.
- README и AGENTS.md, отдельный коммит и push после локальных проверок.
