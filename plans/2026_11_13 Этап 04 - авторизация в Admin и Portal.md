# Этап 4 — авторизация в Admin и Portal

## Результат и границы

Добавить законченный сценарий входа через Go API и PostgreSQL-сессию в обоих интерфейсах.

Сохранить React Admin, статический Portal, существующие цвета и оформление. Не добавлять регистрацию, восстановление пароля, управление пользователями, BroadcastChannel или общий редизайн.

## Реализация интерфейсов

- Повторно изучить текущие Admin, Portal, Nginx и Vite перед изменениями.
- В обоих интерфейсах при открытии проверять /api/auth/me; до завершения проверки не показывать защищённое содержимое.
- Добавить доступные формы с подписями полей, autocomplete, отправкой по Enter и защитой от повторной отправки. Пароль не сохранять в браузерных хранилищах и очищать после запроса.
- В Admin допускать только admin; для employee показывать отказ и кнопку выхода. Существующую проверку состояния переключить на /api/admin/health.
- В Portal показывать ФИО и логин; для администратора без кадровой карточки — логин. Использовать безопасный текстовый вывод.
- Разделить Portal на HTML, CSS и JS без сборщика и библиотек; добавить сообщение для отключённого JavaScript.
- Добавить выход из обоих интерфейсов. Успешный logout очищает пользовательское состояние.
- Сохранить адаптивность, управление клавиатурой, видимый фокус и доступные сообщения об ошибках.

## Состояния и запросы

- Использовать относительный /api/, same-origin cookie и таймаут 10 секунд. Не читать токен из JavaScript.
- Разделять проверку сессии, авторизованное состояние, форму входа, отказ в доступе и временную недоступность.
- 401 при входе означает неверные реквизиты; при проверке сессии — необходимость войти.
- 403 административного запроса означает отказ в доступе; 403 входа или выхода — ошибку настройки Origin.
- 429 показывать с учётом Retry-After; 503 и сетевые ошибки — с возможностью повтора, без утверждения, что сессия завершена.
- При сетевой ошибке или 503 во время logout скрывать защищённое содержимое, показывать, что выход не подтверждён, и предлагать повторить его.
- Обрабатывать пустой ответ 204 без попытки разобрать JSON.
- Использовать счётчик поколений запросов и AbortController: ответы, начатые до выхода или смены состояния, не могут восстановить прежний кабинет.
- Повторно проверять сессию при возвращении вкладки в видимое состояние или фокус, объединяя одновременные проверки.
- Синхронизацию между разными портами обеспечивать повторной проверкой сессии; BroadcastChannel отложить.

## Прокси и локальная разработка

- Сохранить Admin Nginx и добавить Portal отдельный Nginx-конфиг вне публичной статики, подключённый через Compose.
- В обоих интерфейсах /api/ проксировать в Go с удалением префикса.
- Настроить аналогичный proxy Vite на http://localhost:8083, сохраняя исходный Origin.
- Удалить из Portal ссылку на localhost:8083.
- Схему БД и контракт Go API не менять.
- В README явно описать: cookie общая для разных портов одного хоста, но не для localhost и IP сервера. Все используемые origins должны быть разрешены в настройках API.

- Автоматизировать браузерные сценарии с подменёнными API-ответами: роли, отсутствие ФИО, ошибки, logout, 204, 429, истечение сессии и запоздалый /auth/me.
- Собрать Admin, проверить diff и доступные конфигурационные проверки. Недоступные проверки явно перечислить.

На Ubuntu Server после git pull:

- Выполнить Docker-сборку, проверку Nginx и пересоздание затронутых контейнеров.
- Повторить интеграционные тесты CLI в изолированной БД, включая два процесса создания администратора.
- Создать первого рабочего администратора через CLI, если он ещё не существует.
- В Firefox проверить вход, обновление страницы, общий доступ из Admin и Portal на одном хосте, выход и возврат во вторую вкладку.
- Проверить доступ по IP виртуальной машины и мобильную ширину.
- Найденные ошибки исправлять отдельными коммитами.
