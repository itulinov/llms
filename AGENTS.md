# Карта репозитория LMS

Описание проверено по исходникам 12 ноября 2026 года. При изменении архитектуры,
команд или модели данных обновляй этот файл. Фактическое поведение определяют
исходники и конфигурация; это стартовый контекст для новой сессии агента.

## Назначение и текущее состояние

Corporate LMS — разрабатываемая корпоративная система управления обучением.
Стек: Go, React, PostgreSQL и Docker Compose. Интерфейс и комментарии в основном
на русском языке.

Сейчас реализован инфраструктурный каркас: статический портал сотрудника,
админка с проверкой API и БД, минимальный Go API и SQL-модель сотрудников и
оргструктуры, ориентированная на каталоги WebSoft HCM. Курсы, назначения обучения,
CRUD основных полей сотрудников и управление доступом employee реализованы; импорт WebSoft пока отсутствует.
Серверная авторизация и служебные CLI-команды реализованы; интерфейсы входа реализованы.
Пункты меню админки «Сотрудники», «Курсы», «Назначения», «Настройки» — заглушки.

## Связь компонентов

- Портал: `http://localhost:8081`, Nginx монтирует `portal/` только для чтения.
  Nginx проксирует `/api/` в Go, настройки находятся в `nginx/portal.conf`.
- Админка: `http://localhost:8082`. Браузер запрашивает `/api/health` на том же
  origin; Nginx удаляет префикс `/api/` и отправляет запрос в `http://api:8080/health`.
  Для остальных путей работает SPA fallback на `index.html`.
- API: `http://localhost:8083`, внутри контейнера слушает `:8080`.
  Использует стандартный `net/http` и `pgxpool`, без отдельного фреймворка или ORM.
- БД: `postgres:17-alpine`, сервис `db`, база и пользователь `lms`.
  Порт PostgreSQL на хост не опубликован; данные хранятся в именованном томе `pgdata`.
  Compose-проект называется `corporate-lms`.
- API запускается после успешного healthcheck PostgreSQL. Админка зависит от
  запуска API, но отдельной проверки его готовности в Compose нет.

API читает `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, `PGDATABASE`, `PGSSLMODE`.
Compose передаёт их сам, пароль берёт из обязательной переменной `DB_PASSWORD`.

Маршруты в `api/main.go`:

- `GET /health`: Ping БД с таймаутом 3 секунды; при успехе JSON
  `{"status":"ok","database":"connected"}`, при ошибке HTTP 503 и
  `{"status":"error","database":"unavailable"}`.
- `GET /`: JSON `{"service":"corporate-lms-api","language":"go"}`.
  Шаблон `GET /` в ServeMux также обрабатывает прочие не перехваченные GET-пути.

Healthcheck подтверждает соединение с БД, но не наличие прикладных таблиц.

## Модель данных

Ключи и ссылки — UUID с `gen_random_uuid()`. Имена, статусы, связи и важные даты
вынесены в колонки; дополнительные свойства большинства основных сущностей —
в `data jsonb`. `fullname` сотрудника вычисляется БД из частей ФИО.
Для основных карточек триггеры поддерживают `updated_at`.

Основные таблицы:

- `orgs` — организации; `subdivisions` — дерево подразделений каждой организации.
- `cost_centers` — дерево центров затрат.
- `collaborators` — сотрудники; `positions` — штатные единицы в подразделениях.
- `position_commons` — справочник типовых должностей.
- `boss_types` — типы руководителей; `func_managers` — руководители сотрудника,
  подразделения, организации или центра затрат. Заполнена ровно одна из четырёх
  ссылок на управляемый объект, руководитель задан через `person_id`.
- `collaborator_position_history` — история закреплений и основных должностей
  со снимками названий на момент события.
- `collaborator_states` — состояния сотрудника, например отпуск или больничный.
- `websoft_ids` — соответствие внешнего `websoft_id bigint` и UUID LMS с именем
  целевого каталога. При будущем импорте следует использовать это соответствие,
  как описано в комментариях схемы; готового импортера в репозитории нет.
- `v_collaborators` — представление сотрудника с основной должностью,
  подразделением и организацией.

Правила должностей находятся в SQL-функциях и триггерах, а не в Go:

- Сотрудник может занимать несколько должностей, должность занята максимум одним
  сотрудником либо вакантна. Основная хранится в `collaborators.main_position_id`;
  составной внешний ключ проверяет её принадлежность этому сотруднику.
  Поле `positions.is_main` существовало в старой схеме и удалено миграцией `003`.
- При закреплении единственной должности за сотрудником без основной она
  автоматически становится основной.
- Смена `positions.collaborator_id` записывает `assigned`/`unassigned`,
  смена основной должности — `main_set`/`main_unset`. При откреплении основной
  должности ссылка на неё очищается.
- `assignment_start_date`/`assignment_finish_date` описывают закрепление;
  `start_date`/`finish_date` — срок жизни штатной единицы. Даты закрепления занятой
  должности нельзя менять без смены сотрудника. Если дата события не задана,
  используется `current_date`.
- Физическое удаление должностей запрещено триггером: их закрывают статусом.
  Увольнение сотрудника или закрытие должности сами по себе не открепляют его.
- История упорядочивается по `event_seq`; `date` — кадровая дата,
  `created_at` — время записи. Внешний ключ истории на сотрудника не позволяет
  удалить сотрудника с историей; на исторические должности и подразделения
  внешних ключей нет.

## Запуск и миграции

Из корня, с установленными Docker и Docker Compose:

```bash
# Задать DB_PASSWORD в окружении или локальном .env (не коммитить).
docker compose up -d --build
./scripts/migrate.sh
curl http://localhost:8083/health
```

Compose не подключает `schema.sql` к `docker-entrypoint-initdb.d` и не запускает
миграции автоматически. Для обычного развёртывания применяй миграции скриптом.
Полная схема — альтернативный способ создать таблицы в пустой БД и эталон для
сравнения, а не дополнительный шаг после миграций. Её применение само по себе
не заполняет журнал миграций.

`migrate.sh` создаёт `public.schema_migrations`, обходит SQL-файлы по имени,
пропускает записанные версии. Каждая миграция и запись её версии выполняются
в одной транзакции; advisory lock и повторная проверка версии защищают от
одновременного применения одной миграции. Ошибка останавливает скрипт.

История миграций:

1. `001_create_collaborator.sql` — исходная оргструктура и сотрудники с bigint ID.
2. `002_convert_identifiers_to_uuid.sql` — переход на UUID и `websoft_ids`.
   Рассчитана только на пустые прикладные таблицы: проверяет отсутствие строк
   под блокировкой и прерывается при наличии данных. Не является переносом данных.
3. `003_collaborator_main_position.sql` — основная должность в карточке сотрудника,
   даты закрепления, история событий и соответствующие триггеры.

## Работа с изменениями и проверки

При изменении БД добавляй следующую миграцию и синхронно обновляй
`postgres/schema.sql`, чтобы оба способа создания схемы давали одинаковый результат.
Не заменяй уже применённые миграции правкой их содержимого: журнал хранит версии,
но не проверяет контрольные суммы.

Проверки выбирай по затронутой части:

```bash
# БД: нужен работающий Compose-сервис db и заданный DB_PASSWORD.
./scripts/check-schema.sh

# Backend, из api/:
go test ./...
go build ./...

# Админка, из admin/, после установки зависимостей:
npm install
npm run build
```

`check-schema.sh` создаёт и удаляет базы `lms_check_schema` и `lms_check_migr`
в контейнере `db`, сравнивает колонки, ограничения, индексы, триггеры, функции
и представления без учёта порядка колонок. Рабочую базу `lms` не меняет.
Не запускай параллельно несколько проверок: имена временных баз фиксированы.
Эта проверка сравнивает структуру, но не проверяет поведение кадровых операций.

В Go API добавлены unit-, HTTP- и интеграционные тесты авторизации. CI-конфигурации пока нет.
В `admin/package.json` доступны `dev`, `build`, `preview`, но нет `test` и `lint`.
Зависимости админки: React 19, Vite 7, React-плагин Vite 5; lock-файла нет,
Dockerfile использует `npm install`. Go-модуль указывает `go 1.23.0` и
`toolchain go1.24.13`.

Для разработки UI можно запустить `npm run dev` из `admin/`, Vite проксирует `/api/` в `http://localhost:8083` с удалением префикса. Backend локально запускается из `api/`
командой `go run .` с доступной PostgreSQL и переменными `PG*`.

Секреты `.env`, ключи, зависимости, `dist`, дампы и данные БД исключены
через `.gitignore`. Не удаляй том `pgdata` при обычной пересборке.
Условия распространения: Apache 2.0 с Commons Clause; см. `LICENSE` и `NOTICE`.

## Основа авторизации (миграция 004)

`accounts` хранит локальные учётные записи отдельно от сотрудников; `auth_sessions` — хеши серверных сессий. Серверная авторизация реализована; формы входа реализованы. Миграция не создаёт учётных записей. ФИО доступно через существующее `v_collaborators`.
Поведенческая проверка: `./scripts/check-auth-schema.sh` (отдельная временная БД, рабочую `lms` не изменяет).

## Go API: авторизация

`api/config.go`, `password.go`, `store.go`, `auth.go`, `limiter.go` содержат настройки,
Argon2id, PostgreSQL-сессии, HTTP и ограничения входа. Dockerfile собирает весь пакет.
Маршруты Go без префикса: POST /auth/login, GET /auth/me, POST /auth/logout,
GET /admin/health (RequireAuth + RequireRole admin). GET / теперь точный.
Настройки AUTH_* и тестовая AUTH_TEST_DATABASE_URL описаны в README.
AUTH_ALLOWED_ORIGINS обязательна; Compose передаёт настройки из окружения/.env.
Тесты: go test -race ./...; интеграционный TestPostgresSessions требует отдельного
доступного PostgreSQL с правом CREATE DATABASE и создаёт изолированную БД.

CLI в `api/cli.go`: `create-admin --login ...` (скрытый ввод с подтверждением,
только TTY, первый администратор под PostgreSQL advisory lock) и
`cleanup-sessions` (удаление expires_at <= now()). CLI использует только PG*,
AUTH_* проверяются только при запуске HTTP. Подробные Compose-команды — в README.
Интеграционный тест проверяет bootstrap двумя отдельными процессами и очистку.

## Авторизация интерфейсов

Admin использует `admin/src/auth.js`, Portal — идентичный `portal/auth.js`:
проверка сессии, вход, выход, таймаут и защита от запоздалых ответов.
Portal использует `app.js` и `style.css`; `nginx/portal.conf` подключён через Compose
вне публичной статики. Оба Nginx удаляют /api/; Vite делает то же самое.
Admin проверяет /api/admin/health. Сессия обновляется при focus/visibilitychange.
Тесты: `node --test tests/auth.test.mjs`; браузерные проверки Firefox:
`node tests/auth-browser.mjs` после сборки Admin и установки Playwright Firefox.
Серверная приёмка и отложенные CLI-тесты выполняются отдельно после git pull.

## Этап 05: сотрудники

`api/employees.go` регистрирует административные маршруты сотрудников и доступа;
`admin/src/Employees.jsx` — список, карточка, optimistic lock updated_at и доступ.
Схема БД не менялась. Общий adminLock=2026111301 используется также CLI.
Порядок административных блокировок: advisory → collaborators → accounts.
Создание сессии блокирует accounts и повторно сверяет активность и проверенный хеш.
Увольнение отзывает все сессии; восстановление включает даже ручную блокировку.
Последний активный admin защищён; права admin проверяются на всех маршрутах.
Тесты: Go -race, TestPostgresSessions с AUTH_TEST_DATABASE_URL, Firefox
`node tests/employees-browser.mjs` после сборки Admin. Перед рабочей поставкой
обязательны backup и тест восстановления по README.

## Этап 06: оргструктура и должности

`api/structure.go` — организации, подразделения, должности, версии и проверки дерева;
`api/assignments.go` — закрепление, открепление, основная и чтение истории.
Все операции доступны только admin, изменения под adminLock 2026111301.
Кадровые транзакции блокируют сотрудников, затем должности; после триггеров
читают состояние повторно. Даты и события формирует существующая схема,
новой миграции нет. PostgreSQL — источник кадровых правил, React их не дублирует.
`admin/src/Structure.jsx` — три колонки/мобильные экраны;
`Assignments.jsx` дополняет карточку сотрудника. Должности и историю редактировать
напрямую нельзя; закрытие не открепляет, физическое удаление не предоставляется.
Тесты этапа включены в TestPostgresSessions; Firefox: tests/structure-browser.mjs.
Локально проверены PostgreSQL 17, конкурентные назначения/циклы, снимки истории
и основная должность. Рабочая серверная приёмка требует backup и Docker/Firefox.

## Этап 07: оболочка Admin

`admin/src/AdminWorkspace.jsx` — rail 72px, меню 240px, серверные таблицы,
индивидуальное состояние фильтров/страниц и fullscreen dialog с dirty guard
и восстановлением фокуса. App отвечает за вход и подключает workspace.
Employees и Structure переиспользуются в embedded-режиме: initialId,
onDirty/onBusy/onSaved. EntityLookup — серверный поиск и пагинация связей.
Прежняя вложенная трёхколоночная оргструктура больше не точка входа Admin.
Список structure.go дополнен q, статусом подразделений, организацией должностей,
проверкой пары org/subdivision и отображаемыми именами связей. Схема неизменна.
При изменении фильтров offset=0; после save список обновляется, modal остаётся.
При исчезновении строки фокус — «Новая запись». Тест: workspace-browser.mjs;
остальные браузерные регрессии адаптированы к новой навигации.
